# Taskr refresh charter

- Date: 2026-08-04
- Ratified by: owner (SailorDave17), at the charter and verdict gates of cairn's `refresh-project` SOP
- Verdict: **rebuild from charter** — this document is the contract the rebuild is built from,
  written so the rebuild needs nothing else from the legacy code

## The problem (the spirit — this survives whatever happens to the code)

Household chores get allocated by nagging, habit, or an "even split" that isn't actually even.
Taskr allocates them **fairly by time**: chores are minutes of work, people are budgets of
available minutes, and the assignment is proportional to each member's real capacity — then makes
everyone's load visible so the fairness is *seen*, not asserted.

It serves a household with unequal capacities: a kid's 60 available minutes and a parent's 300
should not receive the same chore count.

### What must survive — ratified as all five

1. **Fairness = time-budget allocation.** Proportional to capacity (total → remaining available
   time), never equal counts.
2. **Capability constraints.** A task only goes to someone who can do it (the legacy
   `usersWhoCanDoThisTask` set on a template).
3. **Visibility.** Every member's load and progress on one screen (the legacy all-users view with
   progress bars).
4. **Recurring chores as templates**, instantiated into dated concrete tasks (`TaskTemplate` → `Task`).
5. **Expected-vs-actual time feedback** (`actualWorkTime`), so estimates stop being fiction.

### Explicitly disposable

The 2020 implementation wholesale: Spring Boot 2.4.0 / H2 with DB files committed, vanilla-JS page
swapping, the bootcamp package structure, and the toolchain.

### What "working" means now (the bar, owner-set)

**Phone-usable for a real household**: usable on family members' phones, data survives restarts,
no localhost. Local-demo quality does not meet the bar.

## Assessment summary (measured 2026-08-04)

- **Build**: `./gradlew test` fails at `compileJava` on JDK 17 (`IllegalAccessError` into
  `jdk.compiler` — Gradle 6.6.1 predates it). Reaching a build means an old JDK or toolchain
  surgery; reaching the bar means replacing the platform regardless.
- **Stack**: Spring Boot 2.4.0 (EOL 2021), Gradle 6.6.1, H2 with a live DB file that was tracked
  in git. `dev` also committed a 14.7 MB `ZoomInstaller.exe` into the wrapper directory.
- **Size**: ~3.5k LOC, 57 tracked files (pre-fast-forward count) — small enough that a rebuild is
  honestly scoped.
- **Provenance**: GitHub Classroom team project (2020-Fall-Cohort), five contributors, **no
  license**. The legacy code is not solely the owner's to relicense; the rebuild resolves this by
  writing new code and treating legacy only as a reference.
- **Architecture vs the bar**: desktop pages against `localhost:8080`, DB regenerated by a startup
  populator — no deployment, persistence, or mobile story. The bar fails structurally, not by
  degree; this is what settled the verdict.

## The verdict, with the losers visible

**Rebuild from charter** won. The alternatives and why they lost:

- *Incremental refactor*: its base would be the unreviewed `dev` branch, and after toolchain
  surgery, a Jakarta migration, and a front-end rewrite for phones it converges on a rebuild taken
  by the most expensive route. It also carries the unlicensed co-authored code forward.
- *Targeted modernization*: produces a compiling localhost demo — still below the bar. Right only
  if the bar changes.
- *Archive*: right only if the problem is dead; the owner setting a phone-usable bar says it is not.

**Rebuild home** (owner decision): same repo, on a `rebuild/` branch. Legacy state is tagged
**`legacy-final`** — `main` was first fast-forwarded to `dev` (a strict descendant, +125 commits,
2026-08-04) so the tag captures the project's true front, including the final team week `main` had
never merged. Cutover — the rebuild becoming the default branch content — is the owner's merge
decision at the end of execution, not a step in this document.

## Salvage inventory (carried into the rebuild as reference, not as code)

- **The domain model**: User time budgets (`totalAvailableTime`, `remainingAvailableTime`,
  `userCommittedTime`), Task expected-vs-actual minutes, TaskTemplate capability sets. This is the
  problem statement in nouns and it was right in 2020.
- **The allocation engine as a reference implementation**: `ResourceManager.allocateSingleTask` /
  `allocateAllTasks` / `allocateTasks` at `legacy-final`
  (`back-end/src/main/java/com/taskr/core/ResourceManager.java`) — read it for the fairness
  semantics the team intended, not for the code.
- **The all-users view**: the progress-bar-per-member screen from the final week is the clearest
  statement of spirit item 3.
- **The user icons** (Dad/Bro/Sis/Mom) if wanted — note they are the one asset class with
  unclear provenance.

## Open questions for decomposition (not blockers to starting)

- Target stack for the rebuild — chosen at grooming, not here; the charter constrains outcomes
  (phones, persistence, deployability), never technology.
- Whether allocation ever worked end-to-end in the legacy app is unknown; the rebuild treats the
  legacy behavior as intent, not as an oracle.
- License for the new code — choose one at rebuild start, before outside code arrives.
